# SIGNAL CATS FOOTBALL — протокол 3

Дата: 7 ноября 2026 года. Версия 3 добавляет направление ведения и таймер разворота в полные снимки. Версия 2 добавила серверный мяч, контакты, удар/подкат и матч. Код комнаты — **ровно четыре ASCII-цифры**, например `0427`, ведущие нули сохраняются. Для обеих команд поле ориентировано одинаково: X вправо, Y вверх, синие ворота снизу, красные сверху. Командного переворота ввода/рендера нет.

Дополнение 8 ноября 2026: поле 48×80 м, ворота 11.2×2.4 м. Камера клиента следует своей игровой позиции по X/Y с прежним масштабом обзора. Бинарная схема снимка остаётся прежней.

Ниже приведена действующая схема. Общая нумерация и подтверждения сохраняются между версиями, однако бинарный формат несовместим с версиями 1–2. После обновления сервера открытые вкладки нужно обновить.

## Вход и жизненный цикл

WebSocket `/ws`; управляющие сообщения UTF-8 JSON, полные снимки MessagePack. На сокет один отправитель, надёжная FIFO и один заменяемый ожидающий полный снимок. Внешнее размещение требует HTTPS/WSS. Токенов/аккаунтов/восстановления места пока нет.

```json
{"type":"hello","protocolVersion":3,"name":"Котик","create":true,"code":""}
```

Для входа использовать `create:false,code:"0427"`. Сервер случайно выбирает свободный код в диапазоне 0000–9999; одновременно максимум 64 комнаты по два участника. Первый — blue, второй — red. ID комнаты/матча/игрока и эпоха — серверные непрозрачные строки. Ники очищаются, ограничены 16 графемами и выводятся как текст.

В комнате сразу фаза `training` и один свободный мяч в центре. Один человек может играть до входа второго. Место после обнаруженного обрыва освобождается, пустая комната удаляется. Новому участнику подбирается свободная точка.

| Команда клиента | Поля |
| --- | --- |
| `hello` | Как в примере выше; одно начальное рукопожатие |
| `ping` | `id`, клиентское монотонное `clientTime` |
| `inputBatch` | Identity, `resync`, `frames` (1–4) |
| `cancelAction`, `suspend` | Identity, `throughInputSeq` |
| `startMatch` | Identity; запрос организатора из training/finished |
| `practice` | Identity; возврат организатора к свободной игре |
| `leave` | Identity |

Identity: `roomId`, `matchId`, `connectionEpoch`. Автор определяется сокетом. Чужие/неизвестные ID не управляют состоянием и дают отказ. При переходе в новый матч/практику сервер выдаёт новый matchId и новую эпоху каждому участнику, очищает ввод и посылает новый `welcome`. Поздние пакеты непосредственно предыдущего матча игнорируются. Номера новой эпохи начинаются заново.

Переход `release` дополнительно передаёт `aimX,aimY` — направление стрелки в момент отпускания. Пара должна быть конечным единичным вектором. Сервер использует этот вектор, даже если прицел кадра `InputFrame` уже изменился до отправки пакета. Для существующих клиентов без пары полей сохраняется использование прицела кадра. При ударе сервер переводит контролируемый мяч на сторону прицела, если путь не перекрыт телом/стойкой/бортом. Столкновения с другими игроками сохраняются; собственное тело не отражает выпущенный удар во время выхода мяча.

Быстрый матч допускает 1–2 игроков, без обязательной готовности. Организатор — первый оставшийся участник. Полное лобби, выбор равных составов и готовность относятся к дальнейшей работе.

Фазы: `training`, `countdown` (3 с), `kickoff` (1 с), `playing` (180 активных секунд), `goalPause` (2 с), `finished`. После гола команда, пропустившая мяч, разыгрывает его; в одиночной практике розыгрыш получает присутствующий игрок. В паузах время и управление заблокированы. При нуле времени — результат/ничья. Для нового матча используются новые ID, счёт и ввод сбрасываются.

## Сообщения сервера

| Сообщение | Поля сверх type |
| --- | --- |
| `welcome` | protocolVersion=3, roomId, matchId, playerId, connectionEpoch, team, serverTick, balance, balanceHash, capabilities |
| `roomState` | roomId, matchId, code, phase, organizerId, players:[{playerId,name,team}] |
| `pong` | id, clientTime (эхо), serverTick, serverTime (монотонные миллисекунды) |
| `error` | code, message, fatal; нефатальный отказ не закрывает сокет |
| binary snapshot | Формат ниже |

Ники/состав передаются надёжно и не дублируются в физическом снимке. Баланс неизменен в активной симуляции, SHA-256 — от исходных UTF-8 байтов football.json. Копия в браузере не меняет авторитетные значения. Возможности: training, movement, contacts, ball, kick, tackle, match, targetTick, fullSnapshots.

## Ввод и действия

```json
{
  "type":"inputBatch","roomId":"...","matchId":"...","connectionEpoch":"...","resync":false,
  "frames":[{"inputSeq":1,"targetTick":104,"moveX":0,"moveY":1,"aimX":0,"aimY":1,
    "actionHeld":true,"transitions":[{"kind":"begin","actionId":1,"mode":"kick","possessionVersion":3}]}]
}
```

Каждый кадр — один локальный шаг 60 Гц, штатная пачка — два кадра 30 раз/с. Все поля кадра обязательны; transitions — массив 0–4 переходов. Векторы конечны, компоненты движения -1..1; диагональ нормализуется, аналоговая величина сохраняется. Прицел — ноль или единичный вектор. Координаты/скорость/готовая сила клиента не принимаются как состояние.

Переходы: begin/release/cancel, actionId положительный и возрастающий в эпохе. В режиме с мячом — `mode:kick`, без мяча — `mode:tackle`. Начало связано с актуальным possessionVersion. Сервер проверяет режим, владение, версию, восстановление и перезарядку; заряд определяется серверными тиками. Отпускание ссылается на подготовленное действие, не передаёт доверенную силу. Повтор actionId не создаёт нового удара/импульса. При изменении владения подготовка отменяется, удар автоматически не становится подкатом.

При ударе скорость `10+14q` м/с, q — до 1 за секунду. Владение очищается, собственный повторный захват запрещён 0.2 с. При подкате скорость 13 м/с, дальность 1.8–3.2 м по заряду до 0.6 с; после завершения восстановление 0.2 с, перезарядка 1.5 с от запуска. Упор прекращает скольжение, второй игрок не получает отбрасывания/оглушения/штрафа скорости. Мяч выбивается только при доступном контакте лапы, максимум один раз действием; глобальный запрет захвата 0.15 с после выбивания.

`cancelAction`/`suspend` ставят барьер через последний созданный локальный seq, включая ещё не отправленный кадр. Отмена не является отпусканием. Suspend обнуляет скорость и подготовку, завершает собственное скольжение и отпускает мяч. Возвращение к центру стика, Escape, pointercancel, потеря фокуса/захвата не выполняют действие. Нужен новый жест.

## Общий шаг и подтверждения

Все тела и мяч комнаты движутся одним шагом 1/60 с; не более одного кадра участника на шаг. Снимки каждые 3 тика и при важных переходах. Максимум пять догоняющих общих шагов, без огромного dt и индивидуального ускорения игрока.

Для начальных часов используются три последовательных ping; берётся минимальный RTT, чтобы компиляция первого WebGL-кадра не завысила сетевую задержку. Последующие значения сглаживаются с весом 0.2. Оценка текущего тика: `serverTick + RTT_ms×0.03`, затем +0.06/мс; часы уточняются снимками. Первый targetTick — `floor(оценка)+ceil(RTT_ms×0.03)+2`. Первый кадр создаётся сразу, второй — через один фиксированный шаг, затем отправляется пачка.

Новые inputSeq/targetTick идут последовательно с шагом 1. Применяется движение только кадра, чей targetTick совпадает с текущим общим шагом. Просроченное движение не переигрывается на сервере. При отсутствии кадра используется последнее состояние до тайм-аута 250 мс. Ping, дубли и невалидные сообщения не продлевают ввод. Старые более чем на 15 тиков кадры отбрасываются целиком.

Будущего движения не больше шести кадров; при переполнении старейшее движение отбрасывается, а переходы сохраняются в отдельной ограниченной очереди 32. Будущий горизонт максимум 30 тиков. Начала/отпускания применяются один раз в порядке кадров; просроченные переходы получают текущий серверный тик, без движения назад во времени.

ackInputSeq — наибольший окончательно завершённый номер без ожидающего более раннего принятого кадра. Кадр завершён после решения судьбы движения и всех переходов. Барьер может подтвердить ещё не отправленный номер; соответствующий targetTick также продвигается. Снимок — состояние конца serverTick, даже если ack не изменился.

При коррекции клиент удаляет подтверждённые записи и записи с targetTick≤serverTick, восстанавливает состояние конца тика и повторяет оставшиеся фиксированные шаги. Одного ack для replay недостаточно. Клиент приблизительно предсказывает контакты по последней геометрии, но положение/владение/результат определяет сервер. Визуальная коррекция не проводит игрока через известное препятствие.

После suspend/тайм-аута первая свежая пачка `resync:true` задаёт новый начальный targetTick, seq продолжает расти. Повторная уже принятая пачка идемпотентна. Поздний resync обрабатывается обычными правилами просрочки; сам по себе не закрывает соединение. Фоновые шаги не догоняются. История ограничена 240 кадрами, интерполяция — 60 снимками, задержка 75–150 мс, экстраполяция максимум 100 мс. Чужие игроки и мяч используют одно время рендера; своё ведение отображается относительно предсказанного игрока.

Общие эталоны: test-vectors/movement.json, coordinates.json (обе команды без разворота), input-timeline.json, snapshot.json/msgpack. На шаге 101 fixture имеет ack=1, но локальный seq2 с targetTick=101 всё равно удаляется; повторяется только seq3 и дальнейшие шаги.

## Физика и мяч

Сервер использует непрерывные траектории кругов и общий порядок времени контактов внутри шага. Тела не проталкивают неподвижного соседа; касательная составляющая движения сохраняется. При точном совпадении центров применяется детерминированное разделение. После входа/розыгрыша точки свободны. Сложная неразрешимая группа безопасно останавливается вместо прохода сквозь препятствие.

Состояния мяча: free/controlled/kicked, не более одного ownerId, possessionVersion увеличивается при смене владения. При ведении проверяется путь мяча до позиции перед владельцем, включая тела, борта и стойки. Свободный медленный мяч захватывается доступным игроком, быстрый отскакивает; у игроков нет физического отбрасывания от мяча. Мяч замедляется `exp(-0.9dt)`.

После пользовательского уточнения физический радиус мяча 0.35 м, визуальный 0.72 м, ведение на расстоянии 1.1 м. Визуальный размер близок к прежней голове котика, а отрисовка не позволяет высоким спрайтам скрывать мяч. Проёмы ворот, стойки, отскоки и голы рассчитываются сервером по физическому радиусу. Гол — полное пересечение круга внутри проёма; симметричен, один на эпизод. Контакт стойки имеет приоритет перед голом, гол на точной границе времени допустим, после неё — нет.

## MessagePack

Без сжатия, `[MessagePackObject]`/числовые `[Key]` C#. Объекты — массивы, целые — MessagePack integer, вещественные — float64, UTF-8 строки и bool/nil. Верхний массив **13 элементов**:

| Индекс | Поле |
| --- | --- |
| 0 | protocolVersion=3 |
| 1–3 | roomId, matchId, connectionEpoch адресата |
| 4–6 | snapshotSeq, serverTick, phase |
| 7 | players: массив PlayerSnapshot |
| 8 | recipient: RecipientSnapshot |
| 9 | ball: BallSnapshot |
| 10 | score: [blue,red] |
| 11 | remainingTime: число секунд или nil в свободной игре |
| 12 | phaseEndTick: конец текущего отсчёта/паузы |

PlayerSnapshot, 28 полей:

```text
[playerId,team,x,y,vx,vy,facingX,facingY,preparing,actionId,chargeStartTick,active,
 actionState,preparationMode,slideX,slideY,slideEndTick,recoverEndTick,cooldownEndTick,
 lastActionId,prepareVersion,animationEndTick,dribbleX,dribbleY,dribbleTargetX,dribbleTargetY,
 dribbleTurnStartTick,dribbleTurnEndTick]
```

actionState: idle/running/preparing/sliding/recovering/kicking/celebrating. preparationMode: пустая строка/kick/tackle. Значения тиков — целые, направление скольжения фиксировано после запуска. Костюмы/анимация не меняют физическое тело.

`dribbleX/Y` — единичное направление от котика к мячу, независимое от `facingX/Y` (прицела). При движении ведение следует левому стику/WASD; при остановке сохраняет сторону. Скорость владельца — `runSpeed * dribbleSpeedMultiplier` = 5.04 м/с (90%). Резкая смена направления более чем примерно на 75.5° останавливает владельца: 12 тиков паузы, затем 9 тиков переноса мяча по дуге. В обычном случае бег возобновляется через 21 тик (0.35 с). `dribbleTargetX/Y` и абсолютные `dribbleTurnStartTick/EndTick` позволяют точно продолжить предсказание из любого снимка. Нулевой EndTick означает отсутствие разворота. Изменившаяся в процессе цель может продлить перенос; угловой шаг ограничен, мгновенного переброса нет. Нейтральное движение отменяет разворот и сохраняет текущую сторону. Общие C#/TS векторы — `test-vectors/dribbling.json`.

RecipientSnapshot, 9 полей:

```text
[ackInputSeq,moveX,moveY,aimX,aimY,held,lastInputTick,barrier,needsResync]
```

BallSnapshot, 11 полей:

```text
[x,y,vx,vy,state,ownerId,possessionVersion,captureBlockedUntilTick,
 ownerBlockedId,ownerBlockedUntilTick,impulseSeq]
```

ownerId — nil либо ID присутствующего игрока, только controlled имеет владельца. impulseSeq возрастает при подтверждённом ударе/выбивании, чтобы эффекты не удваивались. Каждый снимок полный и восстанавливает состояние без предыдущего. Клиент проверяет форму, числа, версию, уникальность/принадлежность ID; старые снимки и чужие сессии игнорируются. Три ошибки декодирования прекращают связь с понятным статусом.

Fixture создан настоящим C# кодировщиком и проверяется C#/TS:

```powershell
dotnet run --project server/CatsFootball.Server -c Release --no-build -- --write-fixture shared/test-vectors
```

## Ограничения

16 КиБ суммарно на фрагментированное входящее сообщение, глубина JSON 12; до четырёх кадров/переходов в кадре; token bucket 120 сообщений/с с запасом 120. Входящие команды хоста 256, надёжная исходящая очередь 64, один заменяемый снимок. Отправка/закрытие ограничены 2 с, hello 5 с, тишина WebSocket 15 с. Номера ограничены 2 000 000 000, для исчерпания нужна новая сессия.

Допустим тот же Origin или явный список AllowedOrigins через `;`; нативный CLI без Origin разрешён для этого гостевого протокола. При переполнении надёжной очереди сокет закрывается 4008. Остальные фатальные отказы посылают error и close 4000; штатный выход 1000, остановка 1001. Коды: protocolMismatch, roomNotFound, roomFull, serverFull, invalidMessage, invalidCommand, messageTooLarge, rateLimit, commandQueueFull, timeout; notOrganizer — нефатальный.

Ещё не реализованы: комнаты 3×3, готовность/выбор равных составов в полном лобби, токен возврата/резерв места, автоматическое восстановление участника и нагрузочная приёмка. Публикация и HTTPS-настройка отдельного сервера не выполнялись.
